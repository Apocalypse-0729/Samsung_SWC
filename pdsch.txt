# 📡 README: In-Depth Understanding of PDSCH (Physical Downlink Shared Channel) in LTE

This document provides a **detailed, self-explanatory explanation of PDSCH** in LTE downlink, focusing on:
- Control and data channel interaction (PDCCH–PDSCH)
- MAC–PHY inter-layer communication
- PHY-level PDSCH processing
- Scheduling, resource allocation, MCS, and TBS
- Implementation-oriented understanding

The content is structured slide-by-slide to align with the presentation flow.

---

## Slide 1: Introduction & Motivation

PDSCH (Physical Downlink Shared Channel) is the **primary bearer of user data** in LTE downlink.  
All downlink user-plane traffic is eventually transmitted over PDSCH.

Key performance metrics such as:
- Throughput
- Block Error Rate (BLER)
- Latency
- Spectral efficiency  

are **directly governed by how efficiently PDSCH is scheduled, encoded, and transmitted**.

Understanding PDSCH therefore provides insight into the **entire LTE downlink performance pipeline**.

---

## Slide 2: LTE Channel Architecture

LTE adopts a layered channel architecture to clearly separate responsibilities.

### Channel Classification:
- **Logical Channels** – define the *type of information* (e.g., user data, control data)
- **Transport Channels** – define *how data is transported*
- **Physical Channels** – define *where data is mapped in time and frequency*

### Channel Mapping:
- DTCH (user data)
  → DL-SCH (downlink transport channel)
  → **PDSCH (physical channel)**

Control information follows:
- Control logical channels
  → DL control transport channels
  → **PDCCH**

This architecture explains why **PDSCH always operates under the control of PDCCH**.

---

## Slide 3: Downlink Transmission Flow

The end-to-end LTE downlink data flow is:

Application  
→ RLC  
→ MAC  
→ PHY  
→ RF  

- **RLC** performs segmentation and reassembly
- **MAC** handles scheduling, multiplexing, and HARQ
- **PHY** converts transport blocks into physical signals

A key conceptual split:
> MAC determines *what* and *how much* data to transmit,  
> PHY determines *how* the data is transmitted over the air.

---

## Slide 4: Control Plane vs Data Plane

LTE downlink transmission is logically divided into:
- **Control Plane** – PDCCH
- **Data Plane** – PDSCH

PDCCH does not carry user data.  
Instead, it carries **control instructions** that inform the UE about:
- Whether it has been scheduled
- Where its data is located
- How to decode the data on PDSCH

Without successful PDCCH decoding, **PDSCH decoding cannot even begin**.

---

## Slide 5: PDCCH – Control Channel Explained

PDCCH (Physical Downlink Control Channel) carries **Downlink Control Information (DCI)**.

### DCI conveys:
- Resource block allocation for PDSCH
- Modulation and Coding Scheme (MCS)
- HARQ process ID
- Redundancy version (RV)
- New data indicator (NDI)

PDCCH occupies the **first few OFDM symbols of each subframe**, ensuring it is decoded before PDSCH.

Key dependency:
> PDCCH defines *how*, *where*, and *with what parameters* PDSCH is transmitted.

---

## Slide 6: What is PDSCH?

PDSCH is the **main physical channel for downlink data transmission**.

It carries:
- User plane data (DL-SCH)
- Certain system information under specific conditions

Key characteristics:
- Dynamically scheduled every subframe
- Supports adaptive modulation and coding
- Uses HARQ for reliability
- Flexible time–frequency resource mapping

PDSCH is optimized for **high throughput under varying channel conditions**.

---

## Slide 7: MAC–PHY Inter-Layer Communication

MAC and PHY interact through well-defined interfaces.

### MAC provides PHY with:
- Transport Block (TB)
- Resource allocation type and RB indices
- MCS index
- HARQ process ID
- Redundancy Version (RV)
- Number of transmission layers

### PHY responsibilities:
- Apply coding, modulation, and mapping
- Generate the actual waveform

This separation ensures:
- Modularity
- Scalability
- Independent optimization of MAC scheduling and PHY processing

---

## Slide 8: PDSCH PHY Processing Chain

Once the Transport Block reaches PHY, the following processing occurs:

Transport Block  
→ CRC Attachment  
→ Code Block Segmentation  
→ Turbo Encoding  
→ Rate Matching  
→ Scrambling  
→ Modulation  
→ Layer Mapping  
→ Precoding  
→ Resource Element (RE) Mapping  

Each step transforms the data to ensure **robustness, spectral efficiency, and standard compliance**.

---

## Slide 9: Pre-Processing Details

### CRC Attachment
- Adds a 24-bit CRC for error detection at the receiver

### Code Block Segmentation
- Splits large TBs into smaller blocks to enable efficient turbo decoding

### Turbo Encoding
- Adds redundancy to combat channel errors

### Rate Matching
- Adapts the encoded bitstream to match the selected MCS and allocated resources

These steps are critical for **maintaining BLER targets**.

---

## Slide 10: Scheduling & Resource Allocation

Scheduling decisions are performed at the MAC layer and include:
- UE selection
- Number of allocated Resource Blocks (RBs)
- MCS selection
- HARQ process assignment

### Resource Allocation Types:
- **Type 0** – Bitmap-based allocation using Resource Block Groups (RBGs)
- **Type 1** – Distributed VRBs for frequency diversity
- **Type 2** – Localized contiguous RB allocation (most commonly used)

Localized allocation enables **frequency-selective scheduling** and higher throughput.

---

## Slide 11: Modulation and Coding Scheme (MCS)

MCS defines:
- Modulation order (QPSK, 16QAM, 64QAM)
- Coding rate

MCS is selected based on:
- UE-reported Channel Quality Indicator (CQI)
- Target BLER

This selection balances:
- Throughput maximization
- Decoding reliability

---

## Slide 12: Transport Block Size (TBS)

TBS represents the number of bits transmitted in one subframe.

It is determined by:
- Selected MCS index
- Number of allocated RBs

TBS values are defined in **3GPP standardized tables**, ensuring interoperability and predictable decoding performance.

---

## Slide 13: HARQ in PDSCH

HARQ (Hybrid Automatic Repeat Request) enhances reliability using:
- Multiple parallel HARQ processes
- Incremental redundancy
- ACK/NACK feedback from UE

Instead of retransmitting the same data, additional redundancy is sent, improving decoding probability without restarting transmission.

---

## Slide 14: Implementation-Oriented View

From a code and system perspective, PDSCH processing follows a structured flow:

schedule_pdsch()  
→ determine_resource_allocation()  
→ select_mcs_and_layers()  
→ compute_tbs()  
→ encode_and_map_pdsch()  

Implementations are typically:
- Table-driven (MCS, TBS, CQI)
- Configurable
- Closely aligned with 3GPP specifications

---

## Slide 15: End-to-End Example

Example scenario:
- UE allocated 10 RBs
- CQI reported as 9
- Modulation selected: 16QAM
- Corresponding MCS and TBS chosen
- Encoded bits mapped to OFDM resource elements

This example illustrates the **interaction between scheduling, link adaptation, and PHY processing**.

## Slide 16: Challenges & Optimization Aspects

Practical challenges include:
- Limited PDCCH capacity
- Resource fragmentation
- Throughput vs BLER trade-off
- HARQ timing and feedback delays

Optimizing PDSCH requires careful balancing of **performance, reliability, and control overhead**.

## Slide 17: Summary & Key Takeaways

- PDSCH is the backbone of LTE downlink
- PDCCH fully controls PDSCH transmission
- Strong MAC–PHY coordination is essential
- Scheduling and link adaptation drive performance
- Efficient PDSCH design directly impacts user experience
